# Nothing Fails Quietly

Software has three ways of showing you nothing and they look nearly alike: a page that has not finished drawing, a list with no rows, and something that broke. A reader treats all three as the same answer — there is nothing there — and on a page about an elected official, that assumption is a false statement about the record. This page is the set of rules that keeps the three apart everywhere in the app, and the checks that stop a release when a written rule quietly stops holding in the code.

## What it does

Every page draws itself in the first frame. The heading, the way back out, the actions and the sections the page is made of are knowable from the address alone, so they appear before a single byte comes back, and each region that needs the server fills into a hole already the right shape. Four queries means four regions on four clocks, so one slow read never blanks the screen. The waiting state is a **skeleton**, not a spinner: a spinner says wait, a shape says here is what you are getting and where it will land.

Each region resolves in a strict order — **loading, then error, then empty, then data** — and once a region holds data it keeps showing data, even while it refreshes quietly behind you. A region that could not load reports **inside its own footprint**: what failed, in plain language, with a retry that refetches that region and nothing else. The rest of the page stays usable.

The rule underneath it is hard. **"This failed to load" may never share a branch with "there is nothing here."** On a page about a living public figure, or about a chain of evidence, reporting a network failure as "no record" is a false statement about the world rather than a cosmetic bug. The trap has a second form: the app opens its door before it finishes reading in the movement's data, deliberately, so a large drop of new records cannot look like a failed launch. For those few seconds a roster honestly answers with an empty list. So a region that comes back empty first asks whether the server is still starting, and only then decides that nobody is there. The question is put to the raw answer rather than to filtered rows, because a search that matches nothing is a genuine empty result and has to keep saying so.

Every caught fault is written to **one readable file on the citizen's own machine**, and the message names what the app was trying to do rather than only what broke — "reading the citizen record", then the cause. There is no silent catch anywhere: a failure that is safe to continue past is logged as deliberately non-fatal, so it reads as a decision rather than an oversight. No secret, token or raw request body is ever written there. Repeated identical failures are **folded into one line carrying a count**, and the count goes out either way — on the next occurrence if the storm continues, on a timer if it simply stops. Thirty verbatim copies of one fault delete the history somebody opened the file to read, and the thirtieth copy never told anyone there had been thirty.

Alongside that run the **canaries**. The name is reserved for one class of check and has to be earned three ways: the violation is silent, so nothing crashes and the app keeps working while quietly saying something false; the damage is large; and nothing else can see it, because the check has to read the whole source tree, walk the committed record, or hold two subsystems against each other. They fail the build if the app gains a way to download media it promised never to fetch, if a roll call is excluded with no stated reason, if an enacted instrument on the list charges nobody, if a word this movement refuses to use about a politician reaches rendered copy, if a voting-record term reaches a Flamingo result, or if one award mark is drawn smaller than the one beside it. Each has to cite the written rule it holds and state the real failure it was born from.

## The goal it serves

We ask citizens to check arithmetic over the public record instead of taking anyone's word for it, including ours. A program that makes that argument has to survive the same test it applies to everyone else, and a screen that looks stuck reads as broken. The citizen closes the tab and the argument is lost before it is made.

The worse failure is the one that looks like success. An app that reports a failed fetch as "nobody found" publishes a claim it has no basis for, in the one place a reader takes it at face value — and it does so on the record this movement exists to publish. That is the same harm the [Evidence](/docs/evidence/overview) pillar exists to prevent when a document is withheld on purpose, and it is why the [Flamingo Award](/docs/flamingo/overview) keeps "not earned" and "we have not looked yet" as two different facts rather than two styles of blank. A movement whose whole standard is that a named gap beats a quiet one does not get to run software that hides its own.

The canaries exist for a plainer reason: doctrine that depends on everyone remembering it will quietly stop being true. A promise not to scrape video, a promise that the voting record and everything else never mix, a promise about the words used about a named living person — none of them announces itself when it breaks. Turning them into checks that stop a release is how a movement stops asking to be trusted, which is also why [the whole record is public](/docs/open_data/overview), why [the code is open](/docs/repos/overview), and why the [core loop](/docs/how_it_works/the_core_loop) is something you run rather than something we run for you.

## What keeps it honest

* **The audit of these checks was published rather than quietly fixed.** They were once chained so that the first failure hid every later one; on the day it was measured, thirteen had not run at all and nothing said so. That finding sits in the specification, not in a commit message.
* **One check is deliberately left failing.** It disagrees with a written rule, and which of the two is wrong is a product question, not a test question. A check silenced to turn a suite green is worth less than no check.
* **A canary can only hold a rule somebody wrote down.** It cannot find a promise nobody stated, and it proves nothing about the promises nobody thought to make. This is a ratchet, not a proof of correctness.
* **The step-by-step trail records route decisions, never keystrokes.** Where a citizen went and what the app attempted, not what they typed, and never anything a citizen has not chosen to publish.
* **None of this makes the underlying data right.** It makes failure visible and a false statement harder to ship. Accuracy is a separate discipline: sourcing every row to the official record and letting anyone re-derive it.
