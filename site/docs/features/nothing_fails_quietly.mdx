# Nothing Fails Quietly

Software has three different ways of telling you nothing, and they look almost the same: a screen that never finishes drawing, a list that comes back with no rows, and a message saying something went wrong. Only one of those means what a reader will assume it means. This is the set of rules that keeps them apart on every page, plus a class of automated check that fails the build when a promise the movement made in writing stops being true in the code.

## What it does

Every page draws itself in the first frame. The title, the way back, the actions available and the sections the page is made of come from the route alone, before a single byte arrives, and each region that needs the server fills into a hole already the right shape. A page with four queries has four regions on four separate clocks, so one slow read never holds the other three hostage and never blanks the page. This matters because the app reads flat files from a citizen's own disk, and a read that normally takes forty milliseconds can take twenty seconds with nothing at all wrong.

**Four states are kept strictly apart**: loading, error, empty, and data, in that precedence. Once a region has data it shows data, even while it quietly refreshes behind you. A region that could not load reports inside its own footprint, in plain language, with a working retry that refetches only that region.

The rule underneath all of it: **"this failed to load" may never share a branch with "there is nothing here."** On a page about a living public figure, or about a chain of evidence, reporting a network failure as "no record" is a false statement about the world rather than a cosmetic bug. There is a second version of the same trap. The backend opens its port before it finishes reading in the movement's data, so for a few seconds a roster endpoint honestly answers with an empty list. A region that comes back empty asks whether the server is still starting before it says nobody is on a roster, and it asks about the raw data rather than the filtered rows, because a search that matches nothing is a genuinely empty result and must keep saying so.

Every caught fault is written to **one readable file on the citizen's own machine**. The message names what the app was trying to do rather than only what broke, because that is what makes the trail legible months later to someone who does not have the code open. There is no silent catch anywhere: a failure that is genuinely fine to continue past is logged as deliberately non-fatal. No secret, token, or request body is ever written. Repeated identical failures fold into one line carrying a count, including when the storm simply stops, because a trail that rotates is a trail where volume is a correctness problem: a hundred copies of one fault delete the history somebody came to read.

Alongside that run the **canaries**. A canary is a named class of automated check reserved for rules bigger than any one module, where three things are true at once: the violation is silent, nothing crashes and the app quietly says something false; the damage is large; and nothing else can see it, because the check has to read the whole source tree, walk the committed public record, or hold two subsystems against each other. They fail the build if the app ever gains a way to download media it promised not to fetch, if a roll call is excluded with no stated reason, if an enacted instrument on the list charges nobody, if a word this movement refuses to use about a politician reaches rendered copy, if a voting-record term reaches a Flamingo result, or if one award mark is drawn smaller than the one beside it. Each one has to cite the written rule it holds and name the real failure it was born from.

## The goal it serves

The movement's own standard is that a named gap beats a quiet one. This is that standard turned inward on the software. If we ask citizens to trust arithmetic over the public record rather than trusting us, then the program doing the arithmetic has to be held to the same test it applies to everyone else, and the first place it can fail is by looking confident while knowing nothing. A screen that appears stuck reads as broken, and the citizen closes it. That is not a design complaint; it is the argument being lost before it is made.

The harder failure is the one that looks like success. An app that reports a fetch failure as "nobody found" is publishing a claim about a person or a record that it has no basis for, in the one place a reader will take it at face value. That is the same class of harm the [Evidence](/docs/evidence/overview) pillar exists to prevent when a document has been withheld, and the same reason the [Flamingo Award](/docs/flamingo/overview) keeps "not earned" and "we have not looked yet" as two different facts rather than two shades of grey. A blank has to say which blank it is, in code as much as in copy.

The canaries exist because doctrine that depends on everyone remembering it will quietly stop being true. A promise not to scrape video, a promise that the voting record and everything else never mix, a promise about the words used about a named living person: none of those is expressed by any type system, and none of them announces itself when it breaks. Writing them down as checks that stop a release is how a movement stops having to be taken at its word, which is the same reason the [record itself is public](/docs/open_data/overview) and the same reason the whole thing [can be run on your own machine](/docs/get_started/overview).

## What keeps it honest

* **The guard has been audited and the audit was published, not fixed in silence.** The checks were once chained so that the first failure hid every later one; on the day it was measured, thirteen of them had not run at all and nothing said so. That finding lives in the specification, with the date.
* **One check is deliberately left failing.** It disagrees with a written rule about a fortnight window, and which of the two is wrong is a product question rather than a test question. A check silenced to make a suite green is worth less than no check at all.
* **A canary only holds a rule somebody wrote down.** It cannot find a promise nobody stated, and a rule that is never expressed as a check is a rule that can rot. This is a ratchet, not a proof of correctness.
* **The fault trail is capped and rotates**, so it is a recent history rather than a permanent one, and it records route steps rather than keystrokes. It never carries what a citizen wrote, only where they were and what the app was attempting.
* **None of this makes the data right.** It makes a failure visible and a silent false statement harder to ship. Whether a record is accurate is answered by sourcing it to the official record and letting anyone check it.
